# Plans for the *plan* items

Written 2026-11-03, agreed by the owner 2026-11-04, in the order at the end.
Each plan says what is built, what it changes on servers that already run,
and what needs the owner.
Nothing here changes an existing server's ports, paths or keys without the
owner saying so; new installs get the new default.

## 1. VLESS + REALITY (Vision and XHTTP)

**Why.** Needs no domain or certificate, and borrows a real site's TLS
handshake, so a block on the deployment's own domain does not reach it.

**Build.**
- Agent: `xray_reality_enabled`, `xray_reality_port` (default 8456), a private
  key from `xray x25519`, short ids, and the borrowed site (`dest`, server
  names). Two inbounds: raw TCP + Vision, and XHTTP. Same pattern as SS2022 and
  VLESS Encryption in `xray_config_store.py` and `settings.py`.
- `install.sh --configure`: one more protocol line; it makes the key pair and
  asks for the borrowed site, with a short list checked from Iran as the
  default.
- API: `transport_security="reality"` already exists in the topology model; the
  agent client models (`Literal["none","tls"]`) and the device credential answer
  add the public key and short id.
- App: already reads REALITY links and builds the outbound; it gains the same
  from a server profile.
- Tests: config render, settings validation, API schema, app config; a phone
  test from Iran on a home line and on mobile data.

**Existing servers.** Off until the owner enables it with `--configure`
(opens one new port).

## 2. Everything on port 443

**Why.** One port that looks like any HTTPS site; many Iranian networks treat
odd ports worse.

**Build.**
- nginx `stream` on TCP 443 with `ssl_preread`: the API's name to the API, the
  XHTTP name to Xray's XHTTP, REALITY's borrowed name to REALITY, anything else
  to the API's site. UDP 443 to Hysteria2.
- The API answers `/v1/routes` with 443 addresses first and the old ports after,
  so older apps keep working.
- Tests: an nginx config test in `install.yml` CI; a phone test.

**Existing servers.** This changes ports, so it is off unless the owner says
yes per server. New installs get it by default. The old ports stay open until
the owner closes them.

## 3. AmneziaWG

**Why.** WireGuard with junk packets and changed headers, so DPI that drops
plain WireGuard (ADR 0003) may let it through.

**Build.**
- Server: `amneziawg-go` (userspace, no kernel module) beside WireGuard, with
  its own port and the same peer lifecycle as `drivers/wireguard.py`, plus the
  obfuscation values (Jc, Jmin, Jmax, S1, S2, H1–H4) per server.
- Apps: the Android tunnel uses the amneziawg-android library instead of
  wireguard-android for this protocol; Windows and Linux use `amneziawg-go`.
- This is the largest item: a new engine on four platforms.
- First step: a one-day spike that runs `amneziawg-go` by hand on a test server and tests it from the phone with the AmneziaWG app. Build only if it
  connects where WireGuard does not.

**Existing servers.** Opt-in, with a new port.

## 4. Relay inside Iran

**Why.** Iranian networks reach a server inside Iran more easily; it forwards
to a server abroad over a link that is not filtered the same way.

**Build.**
- A `relay` role for a joined server: no users of its own; Xray inbounds that
  forward to the exit server's XHTTP/REALITY as an outbound (chained, not
  decrypted twice, using Xray's `dokodemo-door` for raw forwarding where
  possible).
- The API lists relay routes as extra addresses of the exit server. The app
  needs no change beyond trying them.
- Uses the existing `--join` and the one node CA.

**Existing servers.** Turning a joined server into a relay changes what it
runs and opens ports on it, so it needs the owner's OK, and the owner chooses
the ports.

## 5. Each user gets only some backup routes

**Why.** One leaked account should not reveal every CDN front and address.

**Build.**
- `/v1/routes` returns a stable subset per account: a hash of the account id
  picks k of n fronts, and the account always keeps the route it last
  connected on.
- An admin setting for k (default: all, so nothing changes until it is set).
- Tests: the same account gets the same subset, accounts are spread across the
  fronts, and a working route stays in the subset.

**Existing servers.** No change until k is set.

## 6. Signed server images and an offline bundle

**Why.** A server inside Iran may not reach Docker Hub or GitHub; an install
should not need them, and should prove what it runs.

**Build.**
- `release.yml` builds the api, worker, admin and agent images, saves them with
  `docker save`, and adds the Xray and Hysteria binaries and `install.sh`
  into one tarball per tag. The tarball goes into `SHA256SUMS` and is signed
  with the same release key, with a GitHub attestation.
- `install.sh --bundle file.tar` checks the signature and loads the images
  without pulling.

**Existing servers.** None; this is a new way to install.

## 7. Upgrade servers from the panel

**Build.**
- Panel → Server → Upgrade to tag X (step-up). The API asks the agent, and the
  agent runs `install.sh --update X` detached (systemd-run, as the deploy runbook
  does).
- Health checks after the run (agent, API, each protocol's check). On failure
  it goes back to the previous tag, which `--update` already records.
- Audited.

**Needs.** It runs as root on the server through the agent, which widens what
the agent can do. That is a security decision for the owner.

## 8. In-app updater

**Build.**
- The app already checks the newest version (`core/updates`). It adds:
  download the APK or installer, check it against the signed `SHA256SUMS`
  (`SHA256SUMS.txt.sig`, key in `docs/release-signers`, pinned in the app),
  then hand it to the system installer. Android uses `REQUEST_INSTALL_PACKAGES`;
  Windows runs the installer.
- Through the tunnel when connected, and from the CDN mirror when GitHub is
  blocked.
- Never installs a file whose signature does not check.

**Needs.** The Android permission shows on the Play-style install screen; the
owner should agree to that.

## 9. iOS and macOS

**Needs.** An Apple developer account ($99/year, paid from outside Iran) and a
Mac to build on. Without both it cannot ship. The work after that is a Network
Extension with Xray (LibXray) and WireGuardKit, about the size of the Windows
work. Paused until the owner has the account and a Mac.

## 10. DNS tunnelling as a last resort

**History.** Started on 2026-10-08 (archive #300) and removed the same day
(archive #301): the server instance, its router, the API endpoint and the
DNS delegation. ADR 0004 still describes the design.

**Why.** When every TCP and UDP route is blocked, DNS queries through the
ISP's resolver usually still get out. It is slow (tens of kbit/s up to about
1 Mbit/s), so it is for messages and the app's own sign-in, not video.

**Build.**
- Server: a DNS tunnel server (dnstt, Noise-encrypted) for one delegated name,
  for example `t.<domain>`, forwarding to a local SOCKS port that only Xray
  uses.
- Port 53 may already be in use on a server. The tunnel then needs a second
  address, or a router in front that splits by name; whatever already runs on
  53 is left as it is.
- API: the tunnel's name and public key in `/v1/routes`, only for accounts that
  have it.
- App: a dnstt client as an engine under Xray (a SOCKS outbound), offered only
  after every other route failed, and labelled slow.
- Tests: route render, app engine selection, a phone test on a line where
  everything else is blocked.

**Needs.** The owner's OK on the port 53 choice and the DNS delegation.

## Order, if all are agreed

5 (small, no server change) → 1 (REALITY) → 2 (443, new installs) →
4 (relay) → 3 (AmneziaWG spike first) → 8 → 10 → 6 → 7. Item 9 waits on the
owner.
